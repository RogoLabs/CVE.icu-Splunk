# TA-cveicu v2.0.0 Design Spec

**Date:** 2026-04-14
**Target Release:** 2026-04-21 (Monday)

## Problem Statement

The modular input fails to register on some Splunk installations, causing the "cve.icu" data input to silently disappear from the UI. Versions 1.0.5 and 1.0.6 attempted fixes, but both were insufficient because:

1. **1.0.5**: Placed the fallback in `__main__`, which was never reached because module-level imports crash first
2. **1.0.6**: Moved the fallback before heavy imports, but it only triggers when `splunklib` fails to import. Since `splunklib` is pure Python, it often imports fine — then the script falls through to `cveicu_lib` imports that pull in `requests → urllib3 → ssl`, which crash on systems with missing SSL shared libraries

The root issue: `splunklib.modularinput.script` itself imports `splunklib.client → splunklib.binding → import ssl`, so even splunklib can fail on broken SSL environments. Our fallback logic tried to be smart about when to use it, and was wrong twice.

Additionally, the existing dashboards use legacy SimpleXML, which is limited and deprecated in Splunk 10.

## Goals

1. Make `--scheme` introspection impossible to break (short of a broken Python interpreter or corrupted `sitecustomize.py`)
2. Provide diagnostic logging when imports fail at runtime so admins can troubleshoot
3. Build a testing framework with CI that catches these issues before release
4. Rework dashboards using Dashboard Studio (Splunk 10+) for a significantly better user experience
5. Add `macros.conf` for configurable index instead of hardcoded `index=main`

## Non-Goals

- No changes to the data ingestion pipeline (stream_events, github_client, cve_processor)
- No changes to the enrichment pipeline (EPSS/KEV)
- No new extracted fields or sourcetypes
- No multi-value field extraction rework (affected_vendor/product stay single-value)
- No backward compatibility with Splunk 8.x/9.x (clean break — major version bump signals this)

## Design

### 1. Bulletproof --scheme Handler

Move `--scheme` handling to the absolute top of `cveicu.py`, before ALL imports except `sys`. The `os` import is deferred until after the `--scheme` exit since `os` is a stdlib module (not a builtin) and could theoretically fail on a broken Python installation.

```python
#!/usr/bin/env python3
import sys

# Handle --scheme before ANY other imports. Splunk calls this at startup
# to register the modular input. If this fails, the input silently
# disappears from the UI with no user-facing error. Only `sys` is needed
# here — it is a builtin module that cannot fail to import.
if __name__ == "__main__" and "--scheme" in sys.argv:
    sys.stdout.write('<scheme>...hardcoded XML...</scheme>')
    sys.stdout.flush()
    sys.exit(0)

import os
# ... rest of imports ...
```

**Key properties:**

- Only `sys` is imported before the check — it is a C builtin, not a stdlib module
- The `__name__ == "__main__"` guard is preserved so that importing this module during tests does not trigger `sys.exit()`
- `sys.stdout.flush()` is called explicitly before exit — stdout is fully buffered when piped (which is how Splunk invokes modular inputs). Without flush, output can be lost. splunklib's own `EventWriter` does this explicitly.
- No conditional logic — `--scheme` always emits XML and exits, unconditionally. The existing `try: from splunklib... / except:` fallback pattern inside the `--scheme` block must be removed entirely — the hardcoded XML is the only code path
- The `get_scheme()` method in the class remains for documentation/reference but is never reached during `--scheme` introspection
- The hardcoded XML must stay in sync with `get_scheme()` — enforced by a CI test
- The hardcoded XML element order must match `Scheme.to_xml()` output: `title`, `description`, `use_external_validation`, `use_single_instance`, `streaming_mode`, `endpoint`. **Note:** the current codebase has `streaming_mode` and `use_single_instance` swapped — this must be corrected during implementation
- The hardcoded XML must remain ASCII-only to avoid encoding issues across locales

**Known limitation:** Python loads `sitecustomize.py` and `usercustomize.py` before any user code runs. If Splunk's Python has a broken `sitecustomize.py` that crashes on import, the script will never reach line 1. This is a Python-level issue no code restructuring can fix. If registration fails even after this fix, admins should check for `sitecustomize.py` in Splunk's Python path.

**`--validate-arguments` handling:** Splunk also calls the script with `--validate-arguments` when users create or edit inputs. This path requires splunklib to parse XML from stdin. Unlike `--scheme` (which runs at startup), `--validate-arguments` only runs when Splunk is already operational, so splunklib should be available. No early fallback is needed, but the diagnostic logging (below) will capture failures clearly.

**Diagnostic logging for runtime failures:**

When the script runs without `--scheme` (i.e., actual data collection or `--validate-arguments`), wrap the import block. Messages use the `ERROR` severity prefix so Splunk categorizes them correctly in `splunkd.log` and they are searchable via `index=_internal sourcetype=splunkd severity=ERROR TA-cveicu`:

```python
try:
    from splunklib.modularinput import Script, Scheme, Argument, Event, EventWriter
    from cveicu_lib.logging_config import setup_logging, get_logger
    from cveicu_lib.credential_manager import CredentialManager
    from cveicu_lib.github_client import GitHubClient
    from cveicu_lib.checkpoint_manager import CheckpointManager
    from cveicu_lib.cve_processor import CVEProcessor
    from cveicu_lib.resource_manager import ResourceManager, TimeoutManager
except (ImportError, OSError) as e:
    sys.stderr.write(
        f"ERROR TA-cveicu: Failed to import required libraries: {type(e).__name__}: {e}\n"
        f"ERROR TA-cveicu: Python: {sys.executable} {sys.version}\n"
        f"ERROR TA-cveicu: sys.path: {sys.path}\n"
    )
    sys.exit(1)
```

The except catches `ImportError` and `OSError` specifically (covers missing libraries and shared object loading failures). Other exceptions (e.g., `SyntaxError` from broken code) propagate naturally with a full traceback, which is more useful for debugging than a generic message.

**Behavior change from v1.0.x:** The current code uses a "degrade gracefully" pattern where if splunklib fails to import, it sets `Script = object` and continues, allowing the class to be defined but crashing later with confusing errors. The new pattern is "fail fast with diagnostics" — if imports fail at runtime, log the exact error and exit immediately. This is deliberately stricter because the old fallback gave users a running-but-broken state with no useful error messages. Note: Splunk will also log its own "exited with code 1" message alongside our diagnostic, so admins will see two error entries.

### 2. Configurable Index via macros.conf

Add `default/macros.conf` with:

```ini
[cveicu_index]
definition = index=main
iseval = 0
```

All saved searches and dashboard base searches use `` `cveicu_index` `` instead of hardcoded `index=main`. Users can override the macro in `local/macros.conf` to point to their chosen index. This is standard practice for Splunkbase apps.

### 3. Testing Framework

Three layers:

#### Layer 1: Unit Tests (no Splunk required)

- **Scheme XML sync test**: Parse both the hardcoded XML string and the serialized output of `get_scheme().to_xml()`. Use order-independent recursive element comparison (sort children by tag + name attribute, compare tag names, stripped text content, attributes, and child count). This catches drift even if splunklib changes element ordering in future versions.
- **Import failure simulation**: Invoke `cveicu.py --scheme` as a **subprocess** with a controlled `PYTHONPATH` and a custom `sitecustomize.py` that poisons `ssl` (`sys.modules['ssl'] = None`). Assert exit code 0 and valid XML on stdout. Do NOT use in-process `sys.modules` manipulation — it is unreliable because modules may already be cached by the test runner.
- **props.conf field extraction test**: Feed sample CVE V5 JSON fixtures through the spath expressions defined in props.conf, verify all expected fields extract correctly.
- **Existing tests retained**: checkpoint_manager, cve_processor, resource_manager, zip_cleanup, epss_kev_command. These exist in `tests/` in the current repo. Test scaffolding (`conftest.py`, `__init__.py` files, `pyproject.toml` for pytest config) must also be added or updated as part of the CI work.

#### Layer 2: Docker Integration Tests

- Use `splunk/splunk:10.0` Docker image (pinned for reproducibility)
- Install from built `.tar.gz` package (not volume mount) to test the real install path
- Tests:
  - Modular input registers: `GET /services/data/modular-input/cveicu` returns 200
  - Data input creation: `POST /services/data/inputs/cveicu/test_input` succeeds
  - Field extractions: ingest sample CVE JSON, query for extracted fields, verify non-null
  - Dashboard loading: `GET /services/data/ui/views/<dashboard_name>` returns 200 for each dashboard
  - Enrichment lookups: verify lookup definition exists
  - Broken environment simulation: run `--scheme` inside the container with SSL stripped from Python path, confirm exit 0 and valid XML

#### Layer 3: GitHub Actions CI Pipeline

Triggers: push to `main`, pull requests.

Three jobs:

1. **Unit tests** — Python 3.9+ matrix, `pytest tests/unit/`, fast (seconds)
2. **AppInspect** — Build `.tar.gz`, run `splunk-appinspect inspect --mode precert`, fail on any error/failure
3. **Docker integration** — Start Splunk 10 container, install package, run `pytest tests/integration/`, tear down

PR gate: all three jobs must pass.

### 4. Dashboard Rework (Dashboard Studio, Splunk 10+)

All dashboards use Dashboard Studio format. Files are `.xml` wrappers in `default/data/ui/views/` containing `<dashboard version="2">` with the JSON definition embedded in a `<definition>` CDATA block:

```xml
<dashboard version="2">
    <label>Dashboard Title</label>
    <description>...</description>
    <definition><![CDATA[
    {
        "dataSources": { ... },
        "visualizations": { ... },
        "layout": { ... }
    }
    ]]></definition>
</dashboard>
```

**Setup page:** `setup_page_dashboard.xml` is preserved as SimpleXML — it is a configuration UI that uses `script="setup_page.js"` for REST API interaction, which Dashboard Studio does not support. This is the only SimpleXML view retained.

All other legacy SimpleXML dashboards are removed: `cve_dashboard.xml`, `cve_dashboard_fast.xml`, `cve_dashboard_instant.xml`, `cve_dashboard_tstats.xml`, `cve_intelligence.xml`.

#### Dashboard 1: CVE Explorer (Analyst)

Daily workhorse for searching and filtering CVEs.

- **Filter bar**: time range, vendor, product, severity, state (published/rejected), CWE category
- **Results table**: CVE ID, title, vendor, product, CVSS score, severity, date published. Sortable columns.
- **Drill-down**: Click any row to see full detail — description, all CVSS versions, ADP data
- **Ingest sparkline**: volume over time to spot large dumps

**Backing searches**: Live searches using `` `cveicu_index` `` macro with lookup enrichment joined at search time.

#### Dashboard 2: Risk Priority (Analyst)

What actually matters. Leads with EPSS + KEV + CVSS enrichment.

- **Top KPIs**: CVEs in CISA KEV, high-EPSS CVEs from last 7 days
- **Risk-ranked table**: CVE ID, CVSS score, EPSS probability, KEV status, SSVC decision, computed risk score
- **Filters**: EPSS threshold, KEV-only toggle, minimum severity
- **Trend chart**: new high-risk CVEs per day/week

**Backing searches**: Live searches using `` `cveicu_index` `` macro joined with `epss_lookup.csv`, `kev_lookup.csv`, `risk_priority_lookup.csv`.

#### Dashboard 3: Vulnerability Landscape (Executive)

High-level posture for leadership and weekly briefings.

- **KPI row**: total CVEs, new this week, critical/high count, % with EPSS > 0.5
- **Severity distribution**: donut or bar chart
- **Top 10 vendors**: by CVE count
- **Trend lines**: CVEs published per week/month
- **KEV growth trend**

**Backing searches**: Scheduled saved searches writing to lookup CSVs for instant loading. Use `| tstats count where sourcetype="cveicu:record"` for basic counts where possible to avoid scanning 300K+ raw events.

#### Dashboard 4: Operational Health (Admin)

Is the add-on working?

- **Input status**: last successful run, events ingested, error count
- **Checkpoint state**: current baseline tag, last delta processed
- **Enrichment freshness**: EPSS/KEV/risk lookup last update timestamps
- **Data volume**: events per day, index size estimate

**Backing searches**: Mix of `index=_internal` queries and lookup metadata.

### 5. Saved Search Performance

The existing saved searches have performance issues that must be addressed:

- **Reduce frequency**: `CVE Total Lookup Refresh` runs every 15 minutes scanning all-time on 300K+ events. Change to hourly. `CVE Daily Summary Lookup Refresh` also scans all-time every hour — change to daily (it computes historical date-based aggregations that don't need frequent updates). Risk Priority Refresh stays at 30 minutes but with a narrower time window.
- **Use `tstats` where possible**: `| tstats count where sourcetype="cveicu:record"` for basic event counts instead of raw `search` commands.
- **Narrow time windows**: Risk Priority Refresh should use `dispatch.earliest_time = -7d` and accumulate, not rescan `-1y`.
- **Add safety settings**: `dispatch.auto_cancel = 600` and `max_concurrent = 1` to prevent pile-up.
- **Stagger cron schedules**: All saved searches offset by at least 5 minutes from each other to avoid concurrent search queue pressure on Splunk Cloud.

### 6. Lookup Size Optimization

The `risk_priority_lookup.csv` could grow to 300K+ rows (15-20MB), hitting Splunk's default `max_memtable_bytes` of 10MB. Fix: only include CVEs with a meaningful risk signal (has EPSS score > 0, OR has CVSS score, OR is in KEV). Most CVEs have none of these — filtering reduces the lookup from ~300K rows to ~50K-80K rows, well within limits.

Document in README that if users hit lookup size limits, they can increase `max_memtable_bytes` in `limits.conf` (requires a support case on Splunk Cloud).

### 7. Search Head Clustering Considerations

The `app.manifest` already declares `_search_head_clustering` support. Key SHC implications:

- **Dashboard Studio views**: Replicate normally via the deployer, same as SimpleXML. No issue.
- **Scheduled saved searches with `outputlookup`**: Writes to the local filesystem of whichever search head the captain assigns. The CSV does NOT automatically replicate to other SHC members. Users on a different search head will see stale or missing data.
- **Mitigation**: Use `| outputlookup replicate=true` in all saved search commands (the `replicate` flag is a search command argument, not a conf file attribute — `transforms.conf` does not support it). Document in README that SHC deployments should deploy via the deployer (`$SPLUNK_HOME/etc/shcluster/apps/`).

## Breaking Changes

This is a **major version bump** (1.0.6 → 2.0.0) signaling backward-incompatible changes:

- **Minimum Splunk version**: Raised from 8.2 to 10.0
- **Legacy dashboards removed**: All SimpleXML dashboards except `setup_page_dashboard.xml` are replaced with Dashboard Studio equivalents. Users on Splunk 8.x/9.x should stay on v1.0.6.
- **Index macro**: All searches use `` `cveicu_index` `` macro. Users who customized saved searches to use a different index will need to set the macro instead.
- **Version constraint**: `app.manifest` `platformRequirements` set to `"Enterprise": ">=10.0"`. Note: this is enforced by Splunkbase downloads and Splunk Cloud vetting, but NOT by self-managed installs. Users can still manually install on Splunk 9 — dashboards will not render but data ingestion will continue to work.
